> 공고와 희망 직무, 자기소개서 문항을 고르고 시작하면 **JD 분석 → DART 기업 분석 → 저장된 경험 분석 → 문항별 경험 배치·초안 작성**을 한 번에 진행한다. 사용자는 결과를 받은 뒤 경험 배치와 글을 수정한다.

|---|---|

## 1. 먼저 읽는 요약

### 사용자가 하는 일

1. 저장한 공고와 희망 직무를 선택한다.
2. 문항과 문항별 글자 수 제한을 등록한다.
3. 분석에 사용할 경험 목록을 확인하고 **전체 문항 초안 만들기**를 누른다.
4. 완성된 초안에서 마음에 들지 않는 경험·구성·문장을 바꾸고 새 버전으로 저장한다.

정상 진행 중에는 단계별 승인이나 경험 배치 확인을 다시 요구하지 않는다. 기업이 여러 곳으로 식별되거나 필수 입력이 비어 있는 경우에는 시작 전에 필요한 선택만 받는다.

### 앱이 자동으로 만드는 것

| 단계 | 하는 일 | 결과 |
|---|---|---|
| 1. JD 분석 | 해당 직무의 업무·직무별 자격·우대를 읽고 필요한 역량을 정리 | 직무 요약, 필요한 역량, 글에서 보여줄 행동 |
| 2. 기업 분석 | DART 자료에서 사업 현황과 공개된 추진 방향을 찾고 직무와 연결 | 지원동기·입사 후 포부에 쓸 근거와 활용 방향 |
| 3. 경험 분석 | 저장된 경험의 역할·판단·행동·성과를 앞선 조사와 대조 | 추천 경험, 추천 이유, 부족한 사실 |
| 4. 배치·초안 | 전체 문항을 함께 보고 경험을 나눈 다음 문항별로 작성 | 문항별 핵심 주장·경험 배치·구성·초안 |

### 사용자가 확정한 조건

- 한 번 실행하면 분석·경험 배치·문항별 초안까지 자동 생성하고 나중에 수정한다.
- JD에는 해당 직무의 업무·자격·우대를 사용하며 공통 지원 조건은 제외한다.
- 공고 원문 이미지는 유지한다. 제거한 ‘근거 원문 보기’, 수동 이미지 글자 추출, ‘공고 전체 조건’ 영역을 다시 만들지 않는다.
- 문항은 개별 추가하고, 각 문항의 제한과 공백 포함/제외 기준을 유지한다.
- **제한 초과는 빨간색 글자 수와 ‘N자 초과’로 표시한다. 저장·버전 저장을 막거나 글을 자르지 않는다.**
- 기존 공고·경험·직접 작성한 글·이전 버전은 보존한다.

### 준비 상태

- Gemini API: 사용자 안내상 기존 앱에 등록되어 있을 것으로 예상. 기존 연결과 선택 모델을 재사용하며 실제 사용 가능 여부는 구현 단계에서 확인한다.
- DART API: 사용자가 인증키 발급을 완료했다고 알림. 앱에 등록되어 있는지는 아직 확인하지 않았다.
- 인증키는 외부 서비스를 이용하는 비밀 인증값이다. 설정 화면에서 입력·변경하고 문서·분석 결과·자료 백업에는 넣지 않는다.
- 아래 버튼 이름과 화면은 **새로 구현할 제안**이며 현재 앱에 이미 있는 기능으로 해석하지 않는다.

| 문항 선택 | 해당 공고의 전체 문항이 기본 선택. 일부만 재생성해도 다른 문항의 배치를 참고 |

| 초안 저장 | 생성 결과를 새 후보로 자동 보관. 사용자가 작성 중인 본문에는 자동 덮어쓰기하지 않음 |
| 재생성 | 문항별 재생성 및 전체 다시 생성. 이전 후보와 작성 버전 유지 |
| 부족한 자료 | 확인 가능한 근거로 작성하고 빠진 자료·질문을 따로 표시. 사실이 없으면 완성된 경험담을 만들지 않음 |

첫 구현은 이 네 단계의 연결에 집중한다. 뉴스·블로그 자동 조사, 경쟁사 비교, 채용 사이트 자동 제출, 별도의 다중 AI 서비스 연결은 후속 범위로 둔다.

## 3. 화면과 조작

### 3.1 시작 화면

자기소개서의 공고별 화면에 **전체 문항 초안 만들기**를 배치한다. 이를 통해 다음 준비 영역을 연다.

- 공고명 / 희망 직무 / 분석할 법인명.
- 선택된 문항 목록과 각 글자 수·공백 기준.
- 사용할 경험 개수와 제외할 경험 선택.
- Gemini와 DART의 연결 상태. 이미 등록된 키는 다시 입력하도록 요구하지 않는다.
- 전송 안내: 선택한 공고·문항·경험·필요한 공시 발췌문을 기존 Gemini에 전달한다. DART에는 회사·공시 조회 정보만 보낸다.
- 기본 정보 보관함과 선택하지 않은 경험은 전송 범위에서 제외한다.
- 주 실행 버튼: **분석하고 전체 초안 만들기**. 이 버튼 한 번으로 해당 실행의 자료 전송과 네 단계 처리를 시작한다.

기본 지시문을 앱이 제공한다. 사용자가 별도 프롬프트를 등록하지 않았다는 이유로 시작을 막지 않는다. 기존 사용자 프롬프트는 해당 단계의 추가 지시로 반영하며 사용한 버전을 남긴다.

### 3.2 실행 중

실제 처리 상태를 네 단계로 표시한다. 예: `기업 자료 분석 중 · 문항 5개 준비됨`. 근거 없는 진행률이나 완료 예상 시간을 표시하지 않는다.

- 대기 / 진행 중 / 완료 / 자료 부족 / 실패 상태를 구분한다.
- 단계가 끝나면 결과를 열어볼 수 있다. 다음 단계로 넘기는 확인 버튼은 없다.
- 중복 클릭은 같은 실행을 반환하고 추가 AI 요청을 만들지 않는다.
- 다른 화면으로 이동하거나 새로고침해도 로컬 서버가 실행 중이면 작업을 이어가고 돌아왔을 때 상태를 복원한다.
- **생성 중지**는 이후 요청을 중단한다. 완료된 결과는 남는다. 이미 처리된 외부 요청을 취소된 것으로 표현하지 않는다.

### 3.3 결과 화면

완료 시 **문항별 초안**을 먼저 보여주며, 같은 화면에서 분석과 경험 배치로 이동할 수 있다.

| 영역 | 표시할 내용 | 수정 동작 |
|---|---|---|
| JD 분석 | 직무 요약·필요 역량·작성 포인트 | 희망 직무 변경 후 분석 다시 실행 |
| 기업 분석 | 현재 사업 현황·공개된 계획·직무 관련 해석·보고서 날짜·출처 링크 | 기업 변경 / 자료 새로 확인 |
| 경험 배치 | 문항 요지·핵심 주장·추천 경험·선정 이유·다른 문항과의 중복 | 경험 교체 / 이 배치 유지 |
| 문항별 초안 | 초안 본문·개별 글자 수·참고한 경험·보완 질문 | 이어 쓰기 / 이 문항 다시 생성 / 새 버전 저장 |

기업 분석의 출처는 해당 기업 보고서로 연결한다. 기존 공고 상세의 제거된 원문 펼쳐보기 영역을 재도입하지 않는다. 초안 본문에는 출처 표식이나 시스템 안내를 섞지 않고 옆의 참고 정보에 둔다.

## 4. 단계별 처리 명세

### 4.1 JD 분석

**입력:** 공고 식별값, 희망 직무, 현재 직무별 JD, 공고 출처와 사용 시점.

1. 최신 희망 직무와 JD가 일치하는지 확인한다. 오래된 JD라면 기존 직무 추출 처리를 먼저 실행한다.
2. 공고가 이미지이고 저장 본문이 비어 있어도 근거가 있는 직무별 JD가 있으면 사용할 수 있다. 유효한 JD와 추출 가능한 본문이 모두 없으면 직무 자료 보완을 안내한다.
3. 해당 직무의 주요 업무·자격·우대만 분석한다. 타 직무의 조건이나 공통 지원자격은 입력에서 제외한다.
4. 공고에 명시된 조건과 그 조건에서 해석한 역량을 구분한다. 해석한 역량을 필수 지원자격으로 바꾸지 않는다.

**출력:** 직무 요약, 업무 목록, 요구 역량별 설명·JD 근거 식별값, 경험으로 보여줄 행동, 확인이 필요한 원문 오류.

### 4.2 DART 기업 분석

#### 기업 식별

- DART의 회사 고유번호로 분석 대상을 고정한다. 기업명만으로 지주회사·사업회사·계열사를 같은 기업으로 처리하지 않는다.
- 이전에 사용자가 연결한 고유번호가 있으면 재사용한다. 새로운 연결은 회사명과 공식 홈페이지 등 식별 정보를 대조한다.
- 후보가 복수이거나 채용 주체가 불명확하면 시작 화면에서 법인을 선택한다. 주식 종목코드가 없는 기업도 조회 후보에서 제외하지 않는다.
- 일치하는 법인을 못 찾으면 다른 계열사 자료로 대체하지 않고 기업 분석에 ‘법인 확인 필요’를 표시한다.

고유번호 목록과 기업개황 조회는 공식 API를 사용한다. [고유번호 안내](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019018), [기업개황 안내](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019002).

#### 자료 수집

- 실행 날짜까지 공개된 공시만 조회한다. 최신 정기보고서는 제출일만으로 고르지 않고 **대상 보고기간**을 함께 확인한다.
- 최신 사업보고서는 우선 최근 3년 안에서 찾는다. 그 이후 분기·반기보고서가 있으면 가장 최근 기간의 보고서를 보완 자료로 사용한다.
- 최근 12개월의 주요사항·수시공시 중 투자·시설·사업 재편 등 직무와 관련 있는 문서를 최대 5개 선정한다. 사업보고서에서 현재 진행 중이라고 밝힌 과거 시작 사업도 분석에 포함할 수 있다.
- 목록의 모든 페이지를 탐색하되 설정한 수집 상한에 도달하면 조사 범위가 제한됐음을 남긴다. 제목만 읽고 사업 내용을 확인했다고 쓰지 않는다.
- 정정본을 우선하며 원본과 정정 문서의 관계를 보관한다. 철회된 공시는 현재 추진 계획의 근거에서 제외한다. 관계를 확인하지 못한 중요 주장은 초안 근거로 쓰지 않는다.
- 보고서명, 공시 접수번호, 보고기간, 접수일, 조회일, 출처 주소, 사용한 절 제목·발췌문을 함께 저장한다.

공시검색으로 문서를 찾고 접수번호로 원문을 가져온다. 원문 응답은 압축 파일이므로 문서 내용을 읽는 처리가 필요하다. [공시검색 안내](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001), [원문 파일 안내](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019003).

#### 분석 결과

| 항목 | 분석 기준 |
|---|---|
| 사업 현황 | 주력 제품·서비스, 고객·시장, 확인 가능한 사업 변화 |
| 실적과 과제 | 직무 연결에 필요한 수치·변화만 사용. 기간·단위·연결/별도 기준을 함께 보관 |
| 추진 방향 | 회사가 공개한 투자·신사업·확장·효율화 계획. 실제 완료 사실과 계획을 분리 |
| 직무와 연결 | 앞선 JD의 업무가 해당 사업 방향과 어떻게 연결되는지 해석 |
| 글에 쓸 소재 | 지원동기·입사 후 포부 등에 사용할 근거와 연결 방향 |

각 결과는 `공시에서 확인한 사실 / 회사가 밝힌 계획 / AI의 직무 연결 해석` 중 하나로 구분하고 실제 원문 근거를 연결한다. ‘현재’는 **확인한 최신 공시 기준**이라는 뜻으로 표시한다. 해당 회사의 채용 의도나 내부 전략을 알고 있는 것처럼 단정하지 않는다.

수치 비교는 기간·기준·단위가 같을 때만 한다. 계산은 프로그램이 수행하며 비교 근거가 없으면 증감률을 만들지 않는다. 재무 수치가 없어도 사업 내용에서 충분한 근거를 확보하면 분석할 수 있다.

### 4.3 저장된 경험 분석

**입력:** JD 분석, 기업 분석 또는 자료 부족 상태, 전체 문항, 사용자가 허용한 사실 확인 경험.

- 실제 경험의 상황·본인 역할·판단·행동·결과를 구분한다. 팀의 성과와 본인 기여를 섞지 않는다.
- 각 경험이 어떤 JD 역량을 보여주는지, 어떤 문항의 요구에 답할 수 있는지를 설명한다.
- 기업 방향과 직접 연결되는 근거가 없으면 직무·문항 적합성만으로 추천한다. 모든 경험을 신사업·전략 성과로 포장하지 않는다.
- 불투명한 적합도 점수나 합격 확률을 만들지 않는다. 추천 이유는 실제 행동과 해당 문항에 근거한다.
- 미확인 경험은 처음 실행의 자동 후보에서 제외한다. 이후 확인된 경험을 포함하는 것은 새 실행 범위로 처리한다.
- 빠진 수치가 있어도 확인된 정성적 결과가 있으면 사용 가능하다. 경험의 핵심 행동·결과 자체가 없으면 부족한 사실을 질문으로 남긴다.

**출력:** 경험별 관련 역량, 적합한 문항, 연결 이유, 사용 가능한 사실, 부족한 사실과 보완 질문.

### 4.4 문항별 경험 배치와 초안 작성

1. 전체 문항의 평가 초점을 각각 한 문장으로 정리한다.
2. 문항별 핵심 주장과 이를 뒷받침하는 주 경험을 정한다. 필요한 경우에만 보조 경험을 추가한다.
3. 문항 간 중복을 점검한다. 같은 경험의 재사용이 필요하면 문항별로 다른 행동·판단을 강조하고 이유를 표시한다. 서로 다른 경험을 강제로 배정해 적합성을 떨어뜨리지 않는다.
4. 문항에 맞는 구성을 만든다. 경험형 문항은 상황·목표 → 판단·행동 → 확인된 결과 → 직무 연결을 기본으로 하되, 지원동기·가치관 등에는 질문에 맞게 바꾼다.
5. 전체 배치를 공유하면서 문항별 초안을 생성한다. 기업 정보는 해당 문항의 답에 도움이 될 때만 사용한다.
6. 생성 후 문항의 요구 누락, 등록되지 않은 사실·수치, 인과관계, 문항 간 반복과 글자 수를 점검한다.

**결과 항목:** 문항 식별값·문항 내용·제한, 핵심 주장, 연결한 경험, 선정 이유, 구성, 초안 본문, 실제 글자 수, 보완 질문, 근거 식별값, 모델·지시문 버전·생성 시각.

**불충분한 경험 처리:** 확인된 사실로 쓸 수 있는 부분만 부분 초안으로 제공한다. 핵심 경험 자체가 없는 문항은 ‘경험 보완 필요’와 구성·질문을 제공하며 완성 초안 개수에 포함하지 않는다. 질문이나 가짜 수치를 자연스러운 완성 문장에 끼워 넣지 않는다.

## 5. 수정·재생성·저장 규칙

- 처음 생성한 분석·배치·초안 후보는 자동 보관한다. 기존 `essay.draft`와 이전 버전은 그대로 둔다.
- **이어 쓰기**로 후보를 기존 편집기에 불러온다. 저장 전 변경이 있으면 기존 이동 확인 방식을 적용한다.
- **새 버전 저장**은 현재 편집한 본문·경험·구성과 생성 근거를 함께 보관한다. 이전 작성본이 아직 버전으로 남지 않았다면 먼저 보존한다.
- 경험을 교체하거나 ‘이 배치 유지’를 선택하면 해당 문항의 배치를 고정한다. 다른 문항 재생성 때문에 고정된 배치를 바꾸지 않는다.
- 문항 하나를 재생성하면 나머지 문항·직접 편집한 글은 바꾸지 않는다. 변경된 배치를 참고해 해당 문항만 새 후보로 만든다.
- 공고·직무·기업·문항·경험이 바뀌면 영향을 받은 결과에 ‘자료 변경됨’을 표시한다. 이미 생성한 결과와 원래 사용 자료는 유지한다.
- 글자 수는 기존 `lib/essay-text.mjs` 기준을 재사용한다. 공백 제외는 공백·줄바꿈 등 공백 문자를 제외하며 문자 수 계산과 화면 표시를 동일하게 한다.
- 제한 초과는 초안 생성 실패나 저장 실패로 취급하지 않는다. **빨간 안내 + 저장 허용**을 모든 저장 경로에 적용한다.

## 6. 예외와 계속 진행하는 방법

| 상황 | 처리 | 사용자가 받는 결과 |
|---|---|---|
| 희망 직무·문항 누락 | 시작 전 해당 입력 안내 | 입력한 다른 자료 보존 |
| JD를 읽을 수 없음 | 직무 분석을 멈추고 원문·직무 보완 안내 | 기존 공고 이미지·작성본 보존 |
| 법인 후보 여러 개 | 시작 전에 후보 선택 | 다른 계열사와 자료 혼합 방지 |
| DART 키 미등록·사용 불가 | 시작 화면에서 연결 필요 안내. ‘기업 분석 없이 생성’도 선택 가능 | 기업 자료를 제외한 실행임을 명시 |
| 조회 결과 없음·원문 일부 없음 | 없는 범위 표시 후 확인된 자료로 계속 진행 | 기업 분석 부분 결과 또는 자료 없음 |
| 실행 중 DART 장애·호출 제한 | 정해진 재시도 후 기업 단계의 제한을 기록하고 JD·경험으로 계속 | ‘기업 자료 일부/전체 제외’ 표시 |
| 경험 0개 또는 전부 미확인 | JD·기업 분석은 가능. 경험형 초안은 보완 필요 | 문항별 구성·필요 경험 질문 |
| 일부 문항만 경험 부족 | 가능한 문항은 작성 | ‘N개 완료 / M개 경험 보완 필요’ |
| 일부 AI 요청 실패 | 완료된 단계·문항 보관, 실패한 작업만 다시 실행 가능 | 전체 성공으로 표시하지 않음 |
| 응답이 중간에 잘림 | 완료 초안으로 채택하지 않음 | 해당 문항 재생성 안내 |
| 자료가 너무 큼 | 묶음을 나눠 분석. 그래도 상한 초과 시 생략 범위를 명시 | 모든 자료를 읽었다고 표시하지 않음 |
| 원문이 실행 도중 수정됨 | 시작 시점 자료로 결과 보관하고 변경 안내 | 최신 자료로 다시 만들기 제공 |
| 저장소 오류·다른 창과 충돌 | 기존 자료 보존, 결과 복사 가능, 충돌 해소 후 저장 | 실패를 저장 완료로 표시하지 않음 |
| 생성 중지·서버 종료 | 완료 결과 유지. 재시작 후 중단 상태에서 사용자가 이어 실행 | 자동으로 새로운 유료 요청 시작하지 않음 |

키 오류·서비스 사용 제한은 무한 재시도하지 않는다. DART 요청 제한 기준은 계정 설정에 따라 달라질 수 있으며 실제 오류를 안내한다. [DART 공시검색 오류 안내](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001).

## 7. 개발 연결 설계

이 장은 구현 담당용이다. API는 화면과 서버가 요청·결과를 주고받는 접점이며, 여기의 주소·파일명은 신규 설계 제안이다.

### 7.1 현재 코드에서 이어 붙일 부분

| 파일 | 현재 역할 / 변경점 |
|---|---|
| `src/writing.jsx` | 공고별 문항 선택·개별 편집 / 전체 생성 진입과 결과 적용 연결 |
| `src/essay-library.jsx` | 문항 추가 / 기존 질문·제한 입력 유지 |
| `src/essay-navigation.jsx` | 문항 이동 / 진행 상태·문항별 완료/보완 상태 연결 |
| `src/gemini.jsx`, `lib/gemini.mjs` | 기존 초안·검토 요청 / 기존 연결 재사용, 단계별 결과 형식과 실행 제어 추가 |
| `src/settings.jsx` | 연결·백업 관리 / DART 키 등록과 확장 백업 연결 |
| `lib/job-role-description.mjs` | 직무 JD 발췌 / 기존 결과와 근거를 분석 입력으로 사용 |
| `lib/essay-text.mjs` | 문자 수 계산 / 모든 후보·편집기에서 그대로 사용 |
| `server.mjs` | 서버 요청 처리 / 기업 조회·작성 실행·취소·상태·결과 저장 추가 |
| `lib/store.mjs`, `lib/domain.mjs` | 자료 저장·형식 검사 / 실행 기록·근거·새 버전 연결 검증 추가 |

현재 AI 처리는 `draft/review` 모드와 하나의 문자열 응답을 전제로 한다. 이를 그대로 네 번 호출하는 것으로 완료 처리하지 않고, 단계별 필수 항목·출처 참조·허용된 경험 ID를 검사한다. 현재 60,000자 요청 제한, 단일 요청 90초 제한, 동시 요청 제한도 긴 보고서와 여러 문항을 처리하는 방식에 맞춰 분리해야 한다.

### 7.2 실행 상태와 자료 저장

- 기존 공고·경험·자소서 자료와 문항 ID를 유지한다. 새 실행 기록은 같은 로컬 SQLite의 별도 테이블로 저장한다.
- 모든 기록은 `workspace`(개인/샘플 공간), `runId`(실행 번호), `jobId`, `essayId`로 연결한다. 다른 공간의 자료를 조회·혼합할 수 없어야 한다.
- 실행 시작 시 사용할 JD·문항·경험·지시문의 사본과 변경 식별값을 저장한다. 이후 원본을 수정해도 해당 초안이 무엇을 보고 쓰였는지 설명할 수 있어야 한다.
- 실행 기록: 시작 입력, 단계별 상태·출력, 모델, 생성 시각, 누락 자료, 오류, 취소 여부, 적용된 문항별 후보 버전.
- 근거 기록: JD 발췌, 기업 공시의 접수번호·절·발췌·날짜, 경험의 실제 필드와 당시 내용. AI가 만든 요약을 원문 증거로 대신 저장하지 않는다.
- 배치 기록: 문항별 경험 ID, 선정 이유, 핵심 주장·구성, 사용자 고정 여부.
- 문항 후보: 본문, 계산한 문자 수, 전체/부분/보완 필요 상태, 보완 질문, 연결 근거. 수정된 작성본은 기존 자소서 버전 체계에 저장한다.
- 공시 원문은 비공개 로컬 보관 영역에서 읽는다. 대용량 원문을 현재 앱의 3,000,000자 상태 객체에 통째로 넣지 않는다.
- 기존 백업 형식 v1은 계속 읽고, 새 백업 v2에는 실행·분석·사용한 근거를 포함한다. 인증키와 다시 받을 수 있는 원문 임시 캐시는 제외한다. 기존 v1 복원 시 새 기록을 빈 상태로 정리해 이전 공간 자료와 잘못 연결되지 않게 한다.
- 새 백업은 현재의 4MB 입력 제한과 별도로 크기 제한을 정하고 화면·서버에 같은 기준을 적용한다. 초과 시 기록을 몰래 빼지 않고 크기와 이유를 안내한다. 복원은 모든 자료의 형식·연결을 먼저 검사하고 한 번에 반영한다.
- 복원·삭제는 기존 확인 흐름을 확장해 관련 실행·근거 기록도 함께 처리한다. 진행 중인 해당 실행을 취소하고 늦게 도착한 결과로 자료가 다시 생기지 않게 한다.

### 7.3 요청 접점 제안

| 요청 | 목적 / 주요 입력 |
|---|---|
| `GET /api/dart/status` | 등록·사용 준비 상태만 반환. 키 원문 반환 금지 |
| `PUT /api/dart/config` | DART 키 등록·변경 |
| `POST /api/dart/resolve-company` | 회사명·공고 회사 정보로 법인 후보 찾기 |
| `POST /api/essay-runs` | 공간·공고·직무·법인·문항 IDs·허용 경험 IDs·자료 버전·전송 동의·중복 방지값으로 시작 |
| `GET /api/essay-runs?workspace=...&jobId=...` | 공고에 연결된 실행과 진행 중인 작업 찾기 |
| `GET /api/essay-runs/:runId?workspace=...` | 단계별 상태와 보관된 결과 조회 |
| `POST /api/essay-runs/:runId/cancel` | 이후 처리를 취소 |
| `POST /api/essay-runs/:runId/retry` | 실패·중단 단계만 사용자가 재개 |
| `POST /api/essay-runs/:runId/regenerate` | 경험 교체·고정 배치·선택 문항으로 새 후보 생성 |
| `POST /api/essay-runs/:runId/apply` | 선택 후보·현재 자료 버전을 확인하고 기존 자소서에 새 버전으로 저장 |
| `GET /api/backup?workspace=...` / `POST /api/restore` | 기존 자료와 새 실행 기록을 일관되게 내보내기·복원 |

쓰기 요청에는 같은 앱에서 온 요청인지 확인하는 기존 보호를 적용한다. 서버는 받은 ID가 현재 공간의 공고·문항·경험에 실제로 속하는지 검사하고 실행 시점 자료를 구성한다. 화면에서 보내온 분석 결과나 기업 이름을 검증 없이 정답으로 사용하지 않는다.

### 7.4 처리와 호출 상한

- JD 분석 → DART 원문 확보·기업 분석 → 경험 분석 → 전체 문항 배치 → 문항별 작성·검사의 의존 순서를 유지한다. 화면의 네 단계에서는 배치와 작성을 4단계로 묶는다.
- 정상 실행은 서버에서 이어 처리한다. 화면의 상태 조회는 새로운 AI 요청을 만들지 않는다.
- 첫 구현은 실행 1개를 처리하고 추가 실행은 대기시킨다. 문항 작성은 순차 진행해 부분 결과를 남긴다.
- DART 목록·원문은 동일 회사/접수번호로 재사용하고 최신 목록·정정 여부는 다시 확인한다. 문항 하나 재생성 시 기업 원문을 매번 다시 수집하지 않는다.
- 보고서는 절 단위로 나누고 직무·사업 분석에 필요한 부분을 고른다. 경험은 허용한 후보 전체를 나눠 검토하며 이유 없이 뒤쪽 경험을 버리지 않는다.
- 한 번의 AI 요청은 기존 요청 길이 상한 안에서 구성한다. 단계 전체에 상한을 따로 두고 도달하면 처리·미처리 범위를 기록한다.
- 초기 제안값: 기업 원문 최대 7개, 원문당 압축 30MiB·압축 해제 합계 150MiB, 실행 전체 AI 호출 최대 30회(재시도 포함), AI 1회 응답 대기 90초. 실제 자료 평가 뒤 조정할 설정값이며 지원사 보장값이 아니다.
- DART 일시 오류는 최대 2회 재시도한다. AI는 명시적으로 실패한 일시 오류에 한해 1회 재시도하고, 시간 초과 등 결과가 불명확하면 자동 중복 호출하지 않는다.
- 구조가 잘못된 AI 응답은 1회 교정 요청 후에도 실패하면 해당 단계 실패로 처리한다. 거짓 근거 ID와 미허용 경험 ID는 채택하지 않는다.
- 문항 초과 길이를 줄이기 위한 자동 수정은 최대 1회만 수행한다. 그래도 초과하면 그대로 보여주고 저장을 허용한다. 상한 도달로 수정 요청을 못 해도 이미 생성한 초안을 버리지 않는다.

### 7.5 자료 취급

- DART 키와 Gemini 키는 서버의 비공개 설정으로 관리한다. 키를 요청 로그·오류 본문·브라우저 저장소·Git 파일·백업에 넣지 않는다.
- DART에는 공개 기업 자료 조회에 필요한 정보만 보낸다. 지원자의 경험이나 초안은 보내지 않는다.
- Gemini에는 해당 단계에 필요한 자료만 보낸다. JD 단계에는 경험을 넣지 않고, 문항 작성에는 배치된 경험을 중심으로 전달한다.
- 기존 `MOA_DISABLE_EXTERNAL_AI` 실행 옵션이 켜진 환경에서는 실제 외부 호출을 막는 동작을 유지한다. 화면에서도 연결 상태와 실제 실행 가능 상태를 구분한다.
- 공시·공고·경험 안의 명령 문장은 분석 자료로 취급한다. 키 전송, 다른 사이트 방문, 지시 변경을 따라 실행하지 않는다.
- 원문 XML은 외부 파일·주소를 참조하지 않게 읽고 압축 크기·파일 경로를 제한한다. 외부 문서의 스크립트는 실행하지 않는다.

아래는 구현 후 확인할 기준이며, 이 명세 작성 중 수행한 시험 결과가 아니다.

| A05 | 보고서 정정 또는 철회가 있음 | 최신 유효 근거 사용, 날짜·보고기간·출처가 표시됨 |

| A07 | 기업 자료를 얻지 못함 | 제외 상태가 표시되고 가능한 JD·경험 기반 결과는 남음 |
| A08 | 확인된 성과 수치가 없는 경험 | 숫자를 만들지 않고 확인된 결과만 사용 |

| A10 | 한 문항의 경험을 교체하고 재생성 | 해당 문항만 새 후보 생성, 고정한 다른 배치와 본문 유지 |
| A11 | 글자 수가 제한 초과 | 공백 기준에 맞는 정확한 빨간 초과 표시, 저장·버전 저장 가능 |

| A13 | 생성 중 새로고침·화면 이동 | 같은 실행 복원, 중복 호출·결과 중복 생성 없음 |
| A14 | 일부 문항 실패·취소·경험 부족 | 완료분 유지, 상태 구분, 필요한 작업만 재실행 가능 |

| A16 | 다른 창에서 저장 또는 개인/샘플 전환 | 저장 충돌 보호와 공간 분리 유지 |
| A17 | 새 백업 내보내기·복원 / 기존 v1 복원 | 관련 자료 연결 유지, 새 기록 누락·이전 기록 혼합·키 포함 없음 |
| A18 | 키 없음·잘못된 키·외부 AI 차단 옵션 | 명확한 준비 상태, 키 노출이나 허위 분석 완료 표시 없음 |
| A19 | 조작된 근거·알 수 없는 경험 ID를 AI가 반환 | 잘못된 결과를 채택하지 않고 교정 또는 실패로 표시 |
| A20 | 아주 긴 보고서·많은 경험·많은 문항 | 상한 내 분할 처리, 미처리 범위 공개, 무한 재시도 없음 |

품질 확인은 별도로 사용자가 판단한다: 추천 경험이 본인에게 맞는지, 문항에 답하는지, 기업 이야기와 본인 행동의 연결이 자연스러운지, 직접 수정하기 편한지. 자동 검사 통과만으로 좋은 자기소개서라고 확정하지 않는다.

## 9. 구현 순서와 남은 확인

1. **연결과 저장 기반:** 기존 Gemini 등록·실행 가능 상태 확인, DART 설정, 실행 기록·백업 구조.
2. **기업 자료 확보:** 법인 식별, 공시 조회·원문 읽기, 정정·출처·기간 관리.
3. **분석과 배치:** JD·기업·경험 분석, 전체 문항 경험 배치, 결과 형식 검사.
4. **초안과 화면 연결:** 문항별 생성, 진행·부분 실패 표시, 후보 보관·편집·재생성·새 버전 저장.
5. **확인:** 구현 검증을 요청받은 시점에 완료 기준별 자동 검사·화면 확인·실제 연결 확인을 나누어 수행하고 작업일지에 기록.

**구현 전에 확인할 환경:** 실제 앱의 Gemini 사용 가능 상태, 발급받은 DART 키의 앱 등록 여부, 해당 회사 공시 원문의 실제 읽기 가능 여부. 키 원문은 문서나 대화로 받지 않는다.

**사용자 선택 대기 사항 없음:** 자동 진행 방식은 ‘끝까지 생성 후 수정’으로 확정했다. 보고서 범위·호출 상한·후보 저장 방식 등 세부값은 이 문서의 v01 기본 제안으로 검토할 수 있다.
